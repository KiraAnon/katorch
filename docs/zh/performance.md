# 性能（中文）

全部数字实测于 MT6897 / Dimensity 8300、MDLA 5.0、fp16、Android 15。

一句话结论：**这颗 NPU 是带宽受限的，而且比你预期的慢。** 所有看起来像优化机会的东西
都测过了，在 8.7 GB/s 这堵墙面前都是噪声。要移植模型的话，先读 §四 再决定要不要花一天做量化。

英文版：[../performance.md](../performance.md)

## 一、端到端：512×512 / 8 步 / 96 秒

| 阶段 | 耗时 |
|---|---|
| DiT 采样（8 步） | 95 s |
| VAE 解码 | 1.3 s |
| 其它 | 0.7 s |
| **稳定态合计** | **96 s** |
| 冷启动首张 | 107 s |

冷启动多出的约 14 秒全是一次性开销：编码器加载 3.1 s、文本编码 5.5 s、NPU 宿主装载 2.75 s，
加杂项。第二张就不再付了。

> 这个项目早先的一份记录写着"文本编码约 25 秒"，**那是错的**。实测日志是
> `文本编码完成 3.0s（257 字符）` / `2.5s（155 字符）`，而且 ComfyUI 自带节点级缓存，
> 同一个 prompt 第二次直接跳过。文本编码从来不是瓶颈。

### 1.1 单步采样的构成

| 项目 | ms | 占比 |
|---|---|---|
| 14 个 blob 的 `run_block` | 10817.9 | 95.5 % |
| 写下一个块的输入 | 163.3 | 1.4 % |
| 读输出 + 缩放 | 209.1 | 1.8 % |
| final layer（fl） | 41.3 | 0.4 % |
| patchify | 25.1 | 0.2 % |
| patch embed（pe） | 23.3 | 0.2 % |
| 归一化 + 写盘 | 15.4 | 0.1 % |
| unpatchify | 11.4 | 0.1 % |
| 时间嵌入传输 | 10.4 | 0.1 % |
| 读 pe 输出 | 4.5 | 0.04 % |
| **合计** | **11328.9** | |

这张表直接判了两件事的死刑：

* `map`/`unmap` 开销只占一步的 **3.3 %**，优化它不可能回本。
* `patchify` + `unpatchify` 合计 **0.3 %**，别碰。

## 二、天花板是访存带宽

| 测量 | 结果 |
|---|---|
| `[1024,2048]` 上串 32 个 MUL | 46.4 ms → **8.7 GB/s** |
| `[4096,4096]` 单个 MUL | 37.2 ms → 2.7 GB/s |

大张量反而更差。这是 MDLA 自己的访存带宽，比手机 LPDDR5（50+ GB/s）低一个数量级——
不是 DDR 的限制，也不是你图里能调的东西。

算总账，一步 DiT：

```
单块搬运  5303 MB  × 14 块  =  74 GB / 步
74 GB ÷ 8.7 GB/s            =  8.5 s    ← 理论下限
实测                           10.8 s    ← 下限的 79%
```

**实现已经跑到硬物理下限的 79%。** 所以"能不能更快"的答案永远是"换策略，不是改代码"。

### 2.1 单算子成本（增量法反推）

| 算子 | 规模 | 耗时 | 反推 |
|---|---|---|---|
| MUL | 4.2 MB | 1.39 ms | 9.1 GB/s |
| **RESHAPE** | — | **0** | 编译期消除 |
| BATCH_MATMUL | 0.27 GFLOP | 3.0 ms | 89 GFLOP/s |
| FC（大） | 1024×2048×2048 | 8.6 ms | ~1 TFLOP/s |
| 每算子固定开销 | — | ~0.6 ms | 从总账反推 |

RESHAPE 真的是零成本——图里 16 个 RESHAPE 一共只要 4 ms。DiT 图里大约有 190 个
（占全部算子的约 33 %），全部免费。

## 三、VAE：37 秒 → 1.3 秒

解码器原来是采样之后第二大的一笔开销，而它是纯卷积栈——正好是 MDLA 的主场。
切成 4 段搬到 NPU：

| 段 | 内容 | 算子 | blob | 耗时 |
|---|---|---|---|---|
| 1 | conv2(1×1) + conv1 + middle + 3×Res | 209 | 28 MB | 0.17 s |
| | CPU 上采样 ×2 | | | 0.04 s |
| 2 | resample conv + 3×Res | 103 | 16 MB | 0.23 s |
| | CPU 上采样 ×2 | | | 0.05 s |
| 3 | resample conv + 3×Res | 98 | 5 MB | 0.34 s |
| | CPU 上采样 ×2 | | | 0.07 s |
| 4 | resample conv + 3×Res + head | 113 | 1 MB | 0.42 s |

**37 s → 1.3 s，28 倍**，肉眼看不出差别：对齐 torch CPU 参考，8bit 像素差最大 2 个色阶，
差异超过 2 的像素占 0.00 %。

**nearest-2× 上采样在 NPU 上做不了。** 自然写法是 reshape + 5 维 CONCAT，而 MDLA 的 CONCAT
只支持最后一维；所有变体（`hw = 8/16/24/32/48/64`）都返回 `rc=-516`。
挪到 CPU 只用 `np.repeat` 跑 0.04–0.07 s，相对收益是舍入误差。

## 四、量化

**实测结论：这颗芯片上 INT8 只快 1.14 倍，而且周边代价让它变成净亏损。别做。**

决定性实验只有二十来行：

| 变体 | FC 1024×2048 @ 2048×2048 |
|---|---|
| fp16 | 8.6 ms |
| W8A16 | 7.6 ms |
| **加速比** | **1.14×** |

不是 2 倍。而为了绕开 INT16 路线里坏掉的那几个算子，每块图要多出约 36 个算子
（DQ/Q 岛边界、用 FC 对 ones 向量替代归约），这把这 14 % 吃光还倒亏：

```
W8A16 路线：17.3 s / 步
fp16  路线：14.6 s / 步
```

全 INT8 数值上还直接崩——每层 22–78 % 误差——所以唯一可行的混合路线是"INT16 + FP16 岛"，
净价值为负。

**INT16 下真正坏掉的算子**（fp16 下完全正常，别把两件事混起来）：

| 算子 | INT16 误差 |
|---|---|
| `MEAN` | 117 % |
| `REDUCE_MAX` | 63 % |
| `REDUCE_SUM` | **200 %，连符号都反了** |

万不得已要量化：把 `sum(x)` 换成 `FC(x, ones)`，实测 0.0000 % 误差。`max(x)` 没有等价物，
只能留在 FP16 岛里。

**`CAST(45)` 不能跨 INT16↔FP16**，会编译失败；但 `DEQUANTIZE(6)` 和 `QUANTIZE(72)` 可以，
岛的边界就是这么搭的。完整的 `INT16 → DQ → MUL → Q → INT16` 往返实测误差 0.0184 %。

## 五、被否决的方向（别再重走）

| 方向 | 结论 | 证据 |
|---|---|---|
| INT8 权重 | ❌ | 8.6 ms → 7.6 ms，只有 1.14× |
| 全 INT8 | ❌ | 每层 22–78 % 误差 |
| 消除 RESHAPE | ❌ | 编译期已消除，零成本 |
| 减少 MUL/ADD | ⚠️ | 手工融合最多省 3.4 %（3935 MB 里的 134 MB） |
| 优化 `map`/`unmap` | ❌ | 只占一步的 3.3 % |
| **合并块（14 → 更少）** | ❌ | 常量 1158 MB，配额 1.35 GB，build 直接 `-314` |
| 复用 cross-attn K/V | ❌ | 实测只省 0.65 %（ctx 只有 512 token） |
| 通用算子融合 | ❌ | MDLA 无融合机制，图格式里没有 fused/in-place 标记 |
| 文本编码缓存 | ❌ | 编码只要 3 s，且 ComfyUI 已经缓存节点 |

### 合并块那个实验的完整证据

把 b00 和 b01 拼成一张图：operand 编号重排、输入重定向。图本身完全合法——2050 个 operand、
无重复、无缺失引用、I/O 正确——build 仍然返回 `-314`（`M_addOp` → 114）。

```
b00 常量：449 个 /  579 MB
b01 常量：449 个 /  579 MB
合并：    898 个 / 1158.5 MB   ← 超 1.35 GB 的 IOVA 配额
```

**14 块切分不是 `map`/`unmap` 的产物，是被常量配额逼出来的。**

## 六、真正剩下的路

只有换策略，没有改实现的空间：

| 方案 | 预估 | 代价 |
|---|---|---|
| 384×384 | 约 70 s | 搬运量降到 56 %；16 块全部重编，构图能力变弱 |
| 6 步而不是 8 步 | 约 87 s | 画质可见下降 |
| **保持 512×512 / 8 步** | **96 s** | 无——当前选择 |

## 七、怎么复现这些测量

脚本在 `tools/`，跑在设备上：

| 脚本 | 测什么 |
|---|---|
| `bench_bandwidth.py` | 稳态访存带宽 |
| `bench_unary_prec.py` | MEAN / SQRT / RSQRT / EXP 在 fp16 下的精度 |
| `bench_reshape.py`、`bench_reshape_mul.py` | RESHAPE 是否真的免费 |
| `bench_op_overhead.py` | 每算子固定开销 |
| `bench_batmatmul.py` | BATCH_MATMUL 吞吐 |
| `analyze_bandwidth.py`、`analyze_graph.py` | 图级搬运量核算 |
| `profile_step.py`、`profile_e2e.py` | 单步 / 端到端分解 |

**跑这些之前先把模型后端停掉。** 在第二个进程里插桩，而 ComfyUI 后端还持有着权重——
这个项目就是这么把手机干到 kernel panic 的（`system_is_deadloomld_on_oomory`）。
把计时放进持有模型的那个进程，或者先停后端。
